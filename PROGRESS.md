- **Security review, open items (none critical or high; for Gary):**
  1. Password pre-hijack: the email provider still accepts `POST /auth/v1/signup` with a caller-chosen password, so an attacker can register a victim's address with a known password and keep it after the victim first signs in by link (or Google). Rotating the password after sign-in was tried and reverted: GoTrue revokes every session on an admin password change, including the one just created. Needs a dashboard-level fix (Confirm email ON in production, and a password-verification hook that rejects every password sign-in if the plan allows it).
  2. No per-IP limit or CAPTCHA on the sign-in and signup actions: anyone can use up the project-wide hourly email cap or mail-bomb an address. PLAN schedules rate limits for M5; signup is already open.
  3. A third party can choose the handle a victim ends up with: the signup action stores the chosen handle in the new user's metadata and `/claim/resume` claims it on the victim's first sign-in. M1-12 step 2 asks for exactly this. Option: make it prefill-only and require the Claim click.
  4. The callback and `/claim/resume` change state on GET (login CSRF, link scanners can burn a token).
  5. `/api/handles/check` and the tenant 404 run unthrottled service-role reads.
  6. An existing account without a page that signs up again with a handle loses it (Supabase ignores `data` for existing users): it lands on `/claim` and picks again.
  7. Every Milestone 2+ screen must call `getAppContext()` itself; the `(screens)` layout does not re-run on soft navigation.
